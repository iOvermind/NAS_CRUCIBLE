# INTERFACE.md 撰寫規範

> 本規範規定 `INTERFACE.md` **該寫什麼、怎麼寫**，以及哪些介面決定必須跨專案一致。
> 通用規範，任何有圖形介面的專案皆適用。

---

## 1. 目的與適用範圍

### 1.1 目的

讓介面的每一個數值都有**依據**可查，而不是每次憑感覺決定。

沒有這份文件時，典型的症狀是：上緣留白 24px、下緣 16px、左右 20px，因為當初只調了上緣就沒再回頭；兩顆並排的按鈕一顆 `text-sm` 一顆 `text-xs`，因為分別在不同時間加上去的。這類問題**不是**靠審美補救，而是靠「這裡該用多少」有唯一答案。

### 1.2 讀者

要**修改或新增畫面**的人。可以假設對方會寫 CSS，但不可假設對方知道這個專案的任何約定。

### 1.3 本規範管什麼、不管什麼

- **管**：`INTERFACE.md` 必須記錄哪些項目、哪些項目必須跨專案一致。
- **不管**：**實作機制**。用 utility class、具名 CSS 類別、CSS-in-JS 還是別的，由專案自行決定——本規範只規定**值與關係**。
- **不管**：畫面該長什麼樣。版型是各專案自己的事（見 §4.3）。

### 1.4 與其他規範的邊界

- 使用者怎麼操作 → `README.md`
- 程式怎麼建置、架構怎麼切 → `DEVELOPER.md`
- 介面的**視覺與行為規格** → `INTERFACE.md`（本規範）

### 1.5 強制語彙

| 用詞 | 意義 |
| :--- | :--- |
| **必須** | 不做就是不合規（MUST） |
| **建議** | 有更好的理由才可以不做（SHOULD） |
| **可** | 自行斟酌（MAY） |

## 2. 檔案位置與命名

- 檔名**必須**為 `INTERFACE.md`，**必須**放在儲存庫**根目錄**。
- 編碼**必須**為 **UTF-8 無 BOM**，換行**必須**為 **LF**，檔尾**必須**留一個換行。
- 語言**必須**為**繁體中文**；token 名稱、CSS 屬性、單位保留原文。
- 沒有圖形介面的專案**不需要**這份文件。

### 2.1 共用 token 與 series

**series** 指一連串有關聯、要看起來像同一套東西的專案，它們共用同一份 token 檔。本規範規定的是**共用的機制**，不是特定的色值。

每個專案**必須**在 `INTERFACE.md` 表明自己屬於哪一種情況：

**獨立專案**——不屬於任何 series：

- token 值由該專案自行決定，**必須**在 `INTERFACE.md` 完整記錄。
- **可**直接採用 [`tokens.css`](tokens.css) 當起點，也**可**完全自訂。

**屬於某個 series 的專案**：

- **必須**與該 series 的其他專案共用同一份 token 檔，且**逐字相同**。
- **必須**在 `INTERFACE.md` 指明所屬 series 與該 token 檔的來源。
- **必須**直接引用或原樣複製該檔，**禁止**手抄色值。
- **禁止**單一專案自行偏離其中幾個值——逐項偏離會讓「逐字相同」失去驗證意義。要改就改整個 series。
- 修改**必須**同步套用到 series 內的全部專案，並以雜湊比對驗證：
  ```powershell
  Get-FileHash <各專案>\docs\rules\tokens.css -Algorithm SHA256
  ```

[`tokens.css`](tokens.css) 是一份**可直接使用的預設起點**（深色配色），不是強制的正典。

## 3. 結構：必要章節 / 選用章節

### 3.1 必要章節（依此順序）

判準是：**照這份文件就能把畫面重建出來**。

| # | 章節 | 必須回答的問題 |
| :-: | :--- | :--- |
| 1 | 適用範圍與視窗尺寸 | 這是什麼型態的畫面？預設與最小尺寸？可否縮放？ |
| 2 | 色票 | 有哪些 token、色值多少、各自用在哪？ |
| 3 | 字體與字級 | 每種用途的字級、字重、行距、字體？ |
| 4 | 間距 | 每種語意間距的名稱、值、用於何處？ |
| 5 | 控制項 | 高度、圓角、內邊距、按鈕角色與各狀態？ |
| 6 | 視覺效果 | 不透明度有哪幾檔？光暈／模糊／漸層用了沒、用在哪、強度多少？ |
| 7 | 狀態與回饋 | 焦點、hover、停用、載入中、錯誤各自怎麼表現？ |
| 8 | 畫面結構 | 版型是什麼樣子？各區塊的職責？ |

**沒有用到的項目必須寫「未使用」，不得刪除章節。** 這樣才分得出「刻意不用」與「忘了寫」——這是本規範最重要的一條。

### 3.2 選用章節

- 動畫與轉場的時間與曲線
- 圖示來源與尺寸
- 響應式斷點
- 文案與用詞慣例

## 4. 撰寫規則

### 4.1 跨專案的一致性分級

每一項介面決定**必須**歸入下列三級之一。同一 series 的專案要看起來像同一套東西，靠的是第一級。

獨立專案（§2.1）沒有共用對象，第一級對它的意義是「**這些項目必須有唯一解並記錄下來**」——不得散落在各處各寫各的。

**必須共用**——逐字相同，不得自訂：

| 項目 | 為什麼 |
| :--- | :--- |
| 色票 token 的名稱與色值 | 這是「同一系列」最直接的來源 |
| 字體堆疊（sans / mono） | 字體一換，親緣感立刻消失 |
| 不透明度檔位 | 決定層次的表現方式 |
| 焦點樣式與停用表現 | 同一套互動語彙，換一個程式不用重學 |
| 日誌／訊息等級的名稱與配色 | 跨程式、跨語言的契約 |

**建議共用**——偏離時**必須**在 `INTERFACE.md` 寫明理由：

- 字級表與行距
- 語意間距的名稱與值
- 控制項高度與圓角

**各自決定**——**禁止**互相套用：

- 版型與畫面結構
- 視窗尺寸
- 有哪些區塊、怎麼排

> 體量差距大的專案硬套同一套版型只會難用。工作站型的編輯器與按一下就跑完的小工具，共用色票已足以看出是同一系列。

### 4.2 間距必須語意化

**禁止**只給一串可用數值就了事——那樣「上緣用 24、下緣用 16」依然合規，問題不會消失。

`INTERFACE.md` **必須**為每一種用途綁定**唯一**的值：

```markdown
| 名稱 | 值 | 用於 |
| :--- | ---: | :--- |
| 視窗外緣 | 20px | 內容距視窗四邊（上下左右一律相同） |
| 區塊間 | 12px | 主要區塊之間 |
| 控制項間 | 8px | 同一列的控制項之間 |
```

規則：

- **四邊外緣必須相等**，**禁止**單獨加大某一邊。
- **禁止**使用表外的值。真的需要新的值，**必須**先修改這張表。

### 4.3 同一列的控制項必須對齊

同一列的輸入框、下拉、按鈕**必須**高度相同、字級相同。**寬度可以不同。**

### 4.4 按鈕

- **必須**定義角色（至少「主要」與「次要」）與各角色的外觀。
- **必須**定義四種狀態：hover、active、disabled、進行中。
- 每個畫面**最多一個**主要按鈕。
- 按鈕文字**建議**用動詞，避免「確定」這類看不出後果的字。

### 4.5 焦點必須可見

- 所有可以用 Tab 走到的元件**必須**有可見的焦點樣式。
- **禁止**只寫 `outline: none` 而不補替代樣式——那會讓鍵盤使用者完全看不出焦點在哪。
- 焦點樣式屬於「必須共用」（§4.1）。

### 4.6 日誌／訊息等級：名稱與顏色都要，且**禁止**只靠顏色

§4.1 把「日誌／訊息等級的名稱與配色」列為必須共用。**配色**在 token 檔裡（`--token-color-level-*`），**名稱**則由下表規定——兩半都是契約的一部分。

| 等級 | 識別字串 | 中譯 | 語意 |
| :--- | :--- | :--- | :--- |
| debug | `DEBUG` | 除錯 | 只在排查問題時需要的細節，預設不顯示 |
| info | `INFO` | 資訊 | 一般進度與結果回報 |
| warn | `WARN` | 警告 | 可以繼續，但使用者應該知道 |
| error | `ERROR` | 錯誤 | 動作失敗或中止 |

規則：

- 這四檔是一條**嚴重度軸線**，對齊 syslog / Python `logging` / Rust `log`。**禁止**把「成功」塞進來——它不是嚴重度，用 `--token-color-status-success`。
- 識別字串**必須**全大寫、逐字如上。**禁止**自創（`WARNING`、`ERR`、`Fatal` 都不行），否則跨程式的日誌無法一起 grep。
- **禁止**只靠顏色傳達等級。理由有二：stdout 導向檔案或在不支援 ANSI 的終端時顏色會消失，等級資訊跟著消失；且只靠顏色傳達資訊不符合無障礙要求。
- 因此每一則訊息**必須**同時帶識別字串或等價的文字前綴（`[!]`、`[x]` 之類），顏色只是**增強**，不是資訊的唯一管道。
- 需要新增等級時**必須**先更新本表與 token 檔，不得在單一專案臨時發明。

### 4.7 視覺效果要記錄，不是要禁止

光暈、高斯模糊、漸層**不禁止**，但**用了就必須**在 §6 寫明：用在哪、強度數值多少。沒用**必須**寫「未使用」。

理由是可預期性：效果本身沒有錯，但「這裡的模糊是 8px 還是 12px」如果沒有答案，下一個人只能再憑感覺加一個。

### 4.8 一般撰寫規則

- 規格**必須**用表格，不用散文。
- 全文**只有一個** H1；必要章節用 H2。
- 數值**必須**帶單位。
- 色值**必須**寫完整的十六進位或 token 名稱，**禁止**只寫「深灰」。

## 5. 範例與註解慣例

- 佔位符**必須**用角括號加繁中描述：`<專案名稱>`、`<色值>`。
- 虛構專案一律用 `MYAPP`。
- 版型示意**建議**用 ASCII 圖，不用截圖——截圖會過時且沒人會記得更新。
- 真的要放截圖時**必須**標明對應的版本號。

---

## 6. 禁止事項

- **禁止**刪除沒用到的必要章節（要寫「未使用」）。
- **禁止**使用 §4.2 的間距表以外的值。
- **禁止**四邊外緣不相等。
- **禁止**同一列的控制項高度或字級不同。
- **禁止**只寫 `outline: none` 而不補焦點樣式。
- **禁止**只靠顏色傳達日誌／訊息等級，或自創 §4.6 以外的等級識別字串。
- **禁止**把「成功」當成一個日誌等級。
- **禁止**自行修改「必須共用」的 token 值。
- **禁止**用「深一點」「大一點」這種無法驗證的描述。
- **禁止**把版型規定成跨專案共用。

## 7. 檢查清單

- [ ] 檔案在根目錄，UTF-8 無 BOM、LF、檔尾一個換行
- [ ] 八個必要章節齊全且順序正確，沒用到的寫「未使用」
- [ ] 每個數值都帶單位，每個色值都是完整色碼或 token 名稱
- [ ] 間距是語意化的，每種用途只有一個值
- [ ] 四邊外緣相等
- [ ] 同一列的控制項高度與字級一致
- [ ] 按鈕的角色與四種狀態都有定義，每畫面最多一個主要按鈕
- [ ] 焦點樣式已定義，且實際程式碼沒有裸露的 `outline: none`
- [ ] 日誌／訊息等級的識別字串與 §4.6 的表逐字一致，且訊息沒有只靠顏色傳達等級
- [ ] 光暈／模糊／漸層：用了有寫強度，沒用有寫「未使用」
- [ ] `INTERFACE.md` 已表明本專案是獨立專案，或屬於哪一個 series
- [ ] 若屬於某個 series，「必須共用」的項目與該 series 的 token 檔一致（雜湊驗證）
- [ ] 「建議共用」若有偏離，已寫明理由
- [ ] 文件描述與實際畫面相符——改了畫面就要回頭改這份
